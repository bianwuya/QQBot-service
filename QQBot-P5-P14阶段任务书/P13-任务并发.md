# P13：任务并发与 Worker 拆分

## 目标

解决当前单工作线程导致“长视频/文件处理堵住普通聊天”的问题。

重点不是无限并发，而是按任务类型隔离。

---

## 1. 目标结构

建议：

```text
Incoming Queue
├── Chat Worker ×2
├── File Worker ×1
├── Media Worker ×1
└── Tool Worker ×1

Social Scheduler ×1
```

数量可以配置，但默认保持保守。

---

## 2. 任务分类

至少区分：

```text
chat
file
media
tool
```

命令按实际执行内容归类。

---

## 3. 顺序保证

同一：

```text
scope + owner
```

的普通聊天必须保持顺序。

不同用户之间允许并行。

Media 任务不能阻塞其他人的 Chat。

---

## 4. SQLite

继续使用 WAL。

必须处理：
- 写锁；
- Busy；
- 事务边界；
- worker 崩溃恢复。

禁止为了并发改成多个不一致数据库。

---

## 5. 出站顺序

同一 job 内的多条出站元素必须保持原顺序。

同一会话的连续聊天回复不能明显乱序。

必要时增加：
- per-conversation lock；
- sequence id；
- delivery barrier。

---

## 6. 模型并发

Chat Worker 数量不能无上限。

默认建议 2。

模型层仍受：
- Sub2API；
- 账号池；
- Model Router

限制。

---

## 7. Media

视频下载/FFmpeg 单独 Worker。

同一时间默认只跑 1 个大视频任务，避免内存/CPU 爆炸。

继续使用现有 process_limits。

---

## 8. 崩溃恢复

继续保持：

- processing -> interrupted；
- sending -> unknown；
- 不自动重跑已付费模型调用；
- 不自动重发 unknown 投递。

并发改造不得破坏这个原则。

---

## 9. 测试

至少覆盖：

1. A 用户长视频时 B 用户聊天仍能完成；
2. 同一用户两条聊天保持顺序；
3. 不同用户可并行；
4. media 并发受限；
5. tool 任务不堵 chat；
6. SQLite Busy 可恢复；
7. worker 崩溃状态正确；
8. delivery 顺序；
9. unknown 语义保持；
10. 原限流继续有效；
11. 全局队列上限继续有效；
12. 每人队列上限继续有效。

---

## 10. 不允许做的事

- 不引入分布式队列。
- 不引入 Redis，除非当前工程已有且任务书另行批准。
- 不取消 SQLite。
- 不一次开大量线程。
- 不改变安全边界。

---

## 11. 完成标准

- Media 不再阻塞普通聊天；
- 不同用户可有限并行；
- 同一用户顺序正确；
- SQLite 稳定；
- 崩溃恢复语义不变；
- 原测试 + 新测试全部通过。
