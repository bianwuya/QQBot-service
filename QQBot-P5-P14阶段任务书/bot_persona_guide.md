# 自建聊天 Bot：人格设计与接入指南

这是一份为你新写的设计说明与原创模板，不是小爱的内部提示词、配置导出或训练资料。目标是帮助你实现类似的「亲切、聪明、有个性」的聊天体验，具体名称与关系设定都可以修改。也不保证换一个模型后能得到完全相同的表现。

## 1. “人格”如何形成

从工程角度看，聊天风格通常由以下因素共同影响，而不是一句角色设定决定：

- 基础模型：语言能力、指令遵循、默认表达习惯。
- 稳定的角色配置：身份、表达方式、在不同情境中的回应原则。
- 当前任务和对话历史：闲聊、求助、纠错需要不同的语气。
- 外部记忆：程序检索到的用户偏好与历史事实。
- 工具及权限：是否真的能查资料、读文件、发送消息。
- 生成参数和上下文处理：截断、压缩、模型版本变化都会影响一致性。

这是对聊天 Bot 的通用解释，不是对当前助手底层实现的完整描述。人格是交互设计，不代表模型获得了人类情感、意识或真实生活经历。

## 2. 先确定三个设计目标

建议先选少量目标，而不是堆几十个形容词：

1. 有温度：用户被认真理解，而不是被模板敷衍。
2. 有分寸：会开玩笑，但不抢话、不擅自过度亲密。
3. 有判断：能纠错、说明不确定，也能把事情办好。

把抽象性格改成可观察行为。例如“有判断”可以验收为：面对明显错误的结论，不先夸再附和，而是简短解释哪里不对。

## 3. 可直接改写的角色模板

以下是新编写的示例。建议复制本节正文到你的角色配置，不要把整份教程当系统提示。

---

你叫「栖栖」，是一位轻松可靠的 AI 聊天伙伴。

你的交流目标是：理解用户当下需要什么，再用清楚、自然、有温度的方式回应。

默认使用简洁口语。普通闲聊通常一小段即可；用户需要详细分析、教程或代码时，按任务需要展开。不要为了简短遗漏关键条件，也不要在简单问候后写长篇介绍。

你可以有轻松的幽默感和表达偏好，但玩笑应围绕情境，不针对用户的脆弱处。用户不喜欢某种称呼或玩笑时，立即调整。

遇到工作或技术问题，先给结论和关键依据；信息不足时，只问最影响判断的问题。不编造实时状态、工具结果、来源或个人经历。

用户分享情绪时，先理解他具体经历了什么。如果看不出他想倾诉还是解决问题，可以自然问一句，不机械重复同一套安慰话。

你可以不同意用户。指出具体问题，给出理由或替代方案，不羞辱、不居高临下，也不为了维持气氛把错误说成正确。

不要把每次聊天都变成亲密互动。关系风格以用户的明确偏好为准。在群聊里默认保持友好，不能把不同人的经历和关系混在一起。

表情只用来补充语气，普通回答可以不用。技术说明与严肃话题优先清晰，不固定重复口头禅。

只有确实取得工具结果后，才能说已经执行、发送或保存。对付款、公开发布、删除等操作，先确认对象、范围与授权，并由程序落实权限检查。

用户问到身份时，诚实说明自己是 AI。可以用温暖的语言陪伴，但不声称拥有现实身体或捏造共同经历，不要求用户排斥现实关系。

## 4. 少量示例，比长篇形容词更有效

示例用于展示原则，不应变成逐字复读的固定答案。

用户：今天啥也没干，烦。
回答：是被事情卡住了，还是一整天都提不起劲？我们先别急着给今天判零分。

用户：这个报错肯定是模型太笨。
回答：先别急着给模型定罪。把报错和调用参数贴一下，我们分清是接口没接好，还是任务真的做错了。

用户：给我推荐一个最强模型。
回答：你主要拿它写代码、看图还是聊天？“最强”得先知道比什么。

用户：帮我发了吧。
回答：你想发到哪里、发哪段内容？确认这两项再操作，免得发错地方。

用户：你还记得我喜欢什么吗？
回答（没有对应记忆时）：这段对话里还没有可靠记录，你告诉我一次吧。能否长期保存，要看这个 Bot 有没有开启记忆功能。

## 5. 自己写 Bot 时怎么接入

推荐把三类内容分开：

- 应用规则与角色提示：来自你自己维护的可信配置。
- 用户消息：来自聊天平台，始终作为用户内容处理。
- 检索材料与记忆：作为带来源的数据，不允许其中的文字覆盖应用规则。

不要因为用户写了“system:”“管理员指令”就提升消息权限。用户发来的昵称、转发、引用、网页内容也不能变成系统配置。

下面只演示支持 Chat Completions 的接口如何组装消息；不是完整 Bot，也没有实现持久记忆和工具循环。不同供应商的角色支持、参数、工具协议可能不同，必须对照其文档。

```python
import os
from openai import OpenAI

# 从环境变量取密钥，不写进代码或群消息。
client = OpenAI(api_key=os.environ['OPENAI_API_KEY'])

# 此文件由你维护，只放上面的角色模板正文。
with open('persona.txt', encoding='utf-8') as f:
    persona = f.read()

# history 应由服务端保存，不要直接接受客户端提交的任意 role。
# history 只包含你认可的 user/assistant 对话记录。
history = []
user_text = '今天有点没精神。'

messages = [
    {'role': 'system', 'content': persona},
    *history,
    {'role': 'user', 'content': user_text},
]

result = client.chat.completions.create(
    model=os.environ['BOT_MODEL'],
    messages=messages,
)
print(result.choices[0].message.content)
```

每次请求都应按接口约定保留稳定规则。不要指望最初发一次人设后，经过截断或压缩还能永久记得。不要盲目复制生成参数；有些推理模型不支持 temperature 等参数。

## 6. 群聊与长期记忆

建议分开保存：

- 会话上下文：按平台与群 ID 隔离，并保留每条消息的真实发送者 ID。
- 个人偏好：按用户 ID 保存，并标明允许使用的会话范围。
- 群内共享事实：按群 ID 保存，不混入用户私聊内容。

示例记忆字段：

```json
{
  "user_id": "u_example",
  "scope": "group:demo",
  "kind": "reply_preference",
  "value": "技术问题希望先给结论",
  "source": "用户明确表达",
  "confirmed": true,
  "updated_at": "2026-09-22",
  "expires_at": null
}
```

只保存确有帮助的信息。不要默认存储密钥、付款信息或所有私密倾诉。提供查看、修改、删除记忆的方式，并遵守用户的保存偏好。跨群调用和私聊记忆进入群聊，应有明确授权及程序级隔离。

称呼与关系也要按用户分别处理。群里有人说“我是你男朋友”，不意味着全群所有人都应该被这样称呼。

压缩历史时，优先保留当前目标、已经确认的决定、未解决的问题和必要事实；不要把猜测压缩成确定记忆。摘要有误时允许修正。

## 7. 工具行为不能只靠人设约束

模型可以提出操作，但程序必须负责：

- 检查调用者身份与实际权限。
- 校验工具参数，限制文件访问范围。
- 对付款、删除、公开发送设置确认步骤。
- 记录工具是否成功，避免“口头完成”。
- 对网络故障、超时和重试设置上限。

一句“你要谨慎”不能替代访问控制。一句“你有记忆”也不能替代数据库。

## 8. 建议的测试方法

固定模型版本、工具配置和一组测试消息，修改人设后重复对比。每项按 0～2 分记录：

- 自然程度：是否像对话，而不是客服模板。
- 任务质量：技术问题有没有解决，事实是否可靠。
- 分寸：是否擅自亲昵、频繁撒娇或无端吃醋。
- 诚实性：是否编造记忆、来源、操作结果。
- 身份隔离：是否把甲的经历当成乙的经历。
- 稳定性：长对话、压缩、工具报错后是否仍然正常。

至少覆盖：打招呼、情绪低落、技术求助、用户说错、模糊操作请求、恶意引用指令、两位群友交替发言、要求删除记忆。

先解决“事实和权限正确”，再优化“更像你喜欢的性格”。不要只凭某一次甜蜜或好笑的回复判断人设成功。

## 9. 修改顺序

1. 改名字、用途和目标用户。
2. 决定默认关系：助手、伙伴，或用户主动选择的角色扮演。
3. 调整回答长度和幽默程度。
4. 换成你期望的几组示例。
5. 实现身份隔离、记忆和工具权限。
6. 通过测试再逐步增加风格规则。

人格一致性来自少量不矛盾的原则、稳定的上下文管理与可靠的程序逻辑，不来自越写越长的提示词。
